# DOOM (2016) on metalgldrv

What DOOM (2016)'s OpenGL renderer (`DOOMx64.exe`, idTech 6) needs from the driver, what this
driver provides, and what to check when it is first run under Wine/CrossOver through the CGL
frontend. docs/crossover.md describes how the driver gets loaded into Wine. Research date: 2026-10-08.

**Confirmed** items cite a source: a public bug, a log, or the apitrace below. **Guesses** are
labelled. The main source is a Windows apitrace of DOOMx64.exe on an AMD HD 5770, attached to Mesa
issue #7078. It holds 1.62 M calls and 669 distinct GLSL shaders. It was parsed end to end to get the
call counts, enum arguments and shader sources used below.

* Trace: https://gitlab.freedesktop.org/mesa/mesa/-/issues/7078
  (file `DOOMx64_b.trace`, brotli-compressed apitrace).
* That driver reports GL 4.3 and exposes no sparse, bindless, draw_parameters or shader_clock
  extensions. A driver that has them may make DOOM take optional paths the trace can't show.

## Context and window system (confirmed)

* **DOOM requests a 4.3 compatibility context** through `wglCreateContextAttribsARB`: MAJOR 4,
  MINOR 3, FLAGS 0, PROFILE_MASK = COMPATIBILITY.
  * It creates four contexts, each shared with the previous one, after a legacy `wglCreateContext`
    on a dummy window.
  * Programs are compiled in one context and drawn in another (also seen by Zink, Mesa !21223 / #8264).
  * Sources: the trace, and Wine bug 43929's `+wgl` logs
    (https://bugs.winehq.org/show_bug.cgi?id=43929).
* **A driver without compatibility contexts fails at start-up** with `FATAL ERROR:
  wglCreateContextAttribsARB failed`.
  * In Wine bug 43929, Józef Kucia wrote: "Mesa doesn't implement compatibility profile which is
    required by the game."
  * radeonsi started working once Mesa 18.2 added the 4.4 compatibility profile
    (https://www.phoronix.com/news/Mesa-18.2-Lands-44-Compat).
  * **What the frontend must do:** create compatibility contexts for this request. metalgldrv
    contexts are 4.6 compatibility unless asked for core.
  * **Risk for CrossOver (docs/crossover.md):** that document assumes DOOM asks for 4.5 core, but it
    asks for **4.3 compatibility**.
    * CrossOver Preview 20260821's `winemac.so` (`macdrv_context_create`) applies its Apple-only
      rejections, "OS X only supports forward-compatible 3.2+ contexts" and "Compatibility profiles
      for GL version >= 3.2 not supported", only to requested versions 3.2–4.1. This comes from
      reading the disassembly; it hasn't been run yet.
    * A 4.3 compatibility request skips them. winemac then passes no `kCGLPFAOpenGLProfile`, so our
      `CGLChoosePixelFormat` sees Legacy and `CGLCreateContext` makes a 4.6 compatibility context.
      No Wine patch is needed for DOOM.
    * To verify, run with `WINEDEBUG=+wgl METALGLDRV_LOG=2` and look for the CGL "created GL 4.6
      compatibility context" line after `wglCreateContextAttribsARB`.
    * Still blocked: compatibility requests for exactly 3.2–4.1, which other titles may make.
      Core 3.2–4.1 requests without the forward-compatible bit can be fixed with
      `CX_FWD_COMPAT_GL_CTX=1` in the bottle environment.
* Pixel format: RGBA8, depth 24, stencil 8, double buffered (`wglChoosePixelFormatARB`).
* **WGL functions DOOM calls:**
  * `wglGetExtensionsStringARB`, `wglChoosePixelFormatARB`, `wglCreateContextAttribsARB`
  * `wglSwapIntervalEXT` (called with 1 and 0)
  * `wglGetSwapIntervalEXT`, once per frame
  * the legacy pixel-format and context calls
* **GLEW loads the GL functions.**
  * Under Wine, opengl32 returns NULL for functions of extensions the driver doesn't advertise, so the
    extension string decides which paths DOOM takes.
  * Wine bug 45826 shows this mattered: DOOM's `GL_EXT_direct_state_access` use broke on Mesa when a
    Wine Staging patch changed it (https://bugs.winehq.org/show_bug.cgi?id=45826).

**Compatibility-profile behaviour used (confirmed, trace):**
* Draws only with VAO 0, from buffer objects, never client arrays.
* Legacy formats: `GL_ALPHA8`, `GL_LUMINANCE8`, `GL_LUMINANCE8_ALPHA8`, `GL_INTENSITY8`.
* `glClampColor(GL_CLAMP_READ_COLOR, GL_FALSE)`.
* `glPolygonMode(GL_LINE)`.
* `glDrawBuffer` / `glReadBuffer(GL_NONE)`.
* `glBindAttribLocation` and `glBindFragDataLocation`.
* Mutable textures (`glTexImage2D(NULL)` plus `GL_TEXTURE_MAX_LEVEL`).
* `GL_SAMPLE_COVERAGE`, `GL_SAMPLE_MASK` / `glSampleMaski`.

The driver supports all of these.

## GLSL (confirmed, trace)

* **All 669 shaders use `#version 430 core` with no `#extension` directives** (455 VS, 455 FS and 35 CS sources).
* Their style comes from an HLSL-like prelude:
  * helpers: `saturate`, `tex2D`, `tex2Dlod`, `texCUBEARRAYbias`, `clip()` with `discard`
  * `textureGatherOffsets` with four offsets
  * unused sampler prototypes
* **Implicit conversions are everywhere:**
  * int to uint in assignments, `out` arguments and returns
  * `const` locals with non-constant initializers
* Uniform blocks have no layout qualifier (shared layout) and get their bindings from
  `glUniformBlockBinding` and `glUniform1i`.
* Resource use:
  * up to 16 samplers, 7 UBOs, 4 SSBOs and 2 images per shader
  * `layout(early_fragment_tests)` in 40 shaders
  * `shared` arrays with `barrier()`
* **Every program compiles, links and passes Metal validation with metalgldrv.**
  * This is 427 programs: each fragment shader paired with the vertex shader before it in the trace,
    plus the compute shaders.
  * The run found one compiler bug, now fixed: `clusterlightsid[base + lights++].x = idx;` on a
    `uint[]` SSBO. A scalar swizzle store on a buffer element generated invalid MSL, and the index
    expression, which has a side effect, was evaluated twice.
  * Read-modify-write of buffer memory (`+=`, `++`, swizzle stores) now evaluates the address once.
    Test: `tests/glsl/exec/bufrmw.comp`.
* **Mesa has no OpenGL drirc entry for DOOMx64.exe.**
  * This was checked across all 561 commits that touched `00-mesa-defaults.conf` and the older drirc files.
  * The only DOOM entries are Vulkan (`DOOMx64vk.exe`: `vk_x11_strict_image_count`, radv DCC and
    invariant-geometry workarounds).
  * The GLSL leniency options often associated with id games belong to RAGE
    (`allow_glsl_builtin_variable_redeclaration`), Wolfenstein: The Old Blood (`force_compat_profile`)
    and Doom 3 BFG.
  * Source: https://gitlab.freedesktop.org/mesa/mesa/-/raw/main/src/util/00-mesa-defaults.conf
* **Depth pre-pass followed by `GL_EQUAL` depth tests without `invariant`.**
  * radv had to force invariant geometry for DOOM (Mesa MR !33933).
  * The profile turns on `vs_position_always_invariant`: `[[position, invariant]]` with
    `preserveInvariance`.

## Vendor, version and VRAM

* **There is no vendor whitelist (confirmed).**
  * An HD 5770, below the minimum spec, runs it.
  * Intel, Mesa radeonsi, r600 and Zink all get past initialization (Mesa #7078 and #8930).
* **DOOM prints `GL_VERSION` but doesn't gate on it.** Its log lists `Vendor :`, `GPU :`, `Driver :` and the
  video memory lines.
* **VRAM detection depends on the vendor string (confirmed):**
  * For `ATI Technologies Inc.`, it queries `GL_VBO/TEXTURE/RENDERBUFFER_FREE_MEMORY_ATI`. The traced
    driver did not even list `GL_ATI_meminfo`, so the choice is made by vendor, not by extension.
  * For NVIDIA, the Wine log shows queries for 0x9047/0x9048/0x9049 (`GL_NVX_gpu_memory_info`).
  * Any other vendor reports `2097151MB` (INT_MAX KiB, meaning "unknown"), and the game still runs.
* The minimum of 2 GB isn't enforced. The Nightmare texture and shadow settings need about 5 GB
  (https://www.tweaktown.com/news/52122/dooms-nightmare-graphics-setting-requires-insane-5gb-vram/index.html).

## The `doom2016` profile

The profile is defined in `src/gl/app_profiles.cpp` and matches `DOOMx64.exe` (see
docs/ARCHITECTURE.md, "Application profiles").

| Setting | Why |
|---|---|
| `GL_VENDOR` = `ATI Technologies Inc.` | **Guess.** This makes DOOM use `GL_ATI_meminfo` instead of "unknown VRAM", and puts it on the AMD path, whose calls and shaders were checked against this driver (above). An NVIDIA vendor string would use `GL_NVX_gpu_memory_info`, but that path may use NVIDIA-only extensions nobody has checked. To undo: `METALGLDRV_VENDOR=metalgldrv`. |
| reported VRAM at most 8192 MB | **Guess.** On unified memory, Metal's recommended working set (about 36 GB on a 48 GB Mac) is the whole GPU budget, shared with the system. The cap keeps the streaming budget in discrete-GPU range while allowing Nightmare settings. To change it: `METALGLDRV_VRAM_MB=<n>`. |
| GLSL quirk `vs_position_always_invariant` | depth pre-pass plus `GL_EQUAL` across programs (above). To undo: `METALGLDRV_GLSL_QUIRKS=-vs_position_always_invariant`. |

Under Wine the executable name is the last path component of the first argv entry ending in `.exe`.
If CrossOver starts the game in a way that hides it, force the profile with
`METALGLDRV_APP_PROFILE=doom2016`. The first context logs the profile in effect:

```
[metalgldrv I] app profile 'doom2016' (exe DOOMx64.exe), vendor "ATI Technologies Inc.", VRAM at most 8192 MB, GLSL quirks [vs_position_always_invariant]
```

## Driver changes made for DOOM

* `GL_ATI_meminfo` and `GL_NVX_gpu_memory_info`:
  * They report Metal's `recommendedMaxWorkingSetSize` (total) and that minus `currentAllocatedSize` (available), in KiB.
  * Eviction counts are 0, and the ATI auxiliary memory fields are 0.
* `glBindFramebufferEXT` and `glBindRenderbufferEXT`:
  * They had been weak stubs that did nothing, although `GL_EXT_framebuffer_object` was advertised.
  * They follow EXT semantics: names that were never generated are created on bind, in every profile.
* Other entry points of advertised extensions that were stubs:
  * `glBufferDataARB`, `glBufferSubDataARB`, `glGetBufferSubDataARB`
  * `glGetn*ARB`
  * `glTexImage3DEXT`, `glFramebufferTextureFaceARB`, `glClearColorI{i,ui}EXT`
  * `glVertexAttribP{1,2,3}ui[v]`
* **Pixel unpack buffer uploads now copy on the GPU** when the data needs no conversion (compressed
  blocks, and uncompressed formats whose layout matches the Metal format).
  * DOOM's page transcoder writes PBOs with a compute shader, then uploads compressed pages from them.
  * Before this change, every such upload waited for the GPU to finish writing (a CPU stall) and then
    copied the data through the CPU.
  * Now the copy is a buffer-to-texture blit in stream order. A barrier is added when a dispatch wrote
    the buffer earlier in the same encoder.
* GLSL fixes:
  * buffer read-modify-write evaluates the address once
  * scalar swizzle stores into buffers now work
* Application profiles: string, extension, VRAM and GLSL-quirk overrides.
* Diagnostics: `METALGLDRV_LOG_UNSUPPORTED=1` logs once per unique item. It covers stub calls,
  unknown `GetProcAddress` names, `INVALID_ENUM` and other GL errors, and unsupported `#extension`
  requests. It also dumps failed compiles and links to `METALGLDRV_DUMP_DIR`.

## Not done, and why

* **ARB_bindless_texture.** DOOM's GL path never used it in the trace, and the Intel path, which has
  no bindless, runs. A Metal implementation is feasible: a handle-table buffer of
  `MTLResourceID`s, read in MSL through `device` structs of texture types. That was checked to
  compile, but it is a large compiler change with no known consumer.
* **EXT_direct_state_access.** DOOM has a fallback. Advertising it would mean implementing the whole
  extension, because GLEW marks the extension unavailable when any entry point is missing.
  Implementing only the eight functions DOOM calls and advertising it would be incorrect.

## Unknown until it runs

* Whether DOOM on a 4.6 driver with these extensions takes paths the 4.3 trace doesn't show, for
  example `ARB_shader_draw_parameters`, sparse textures or `ARB_multi_draw_indirect`. If it does,
  `METALGLDRV_HIDE_EXTENSIONS` can hide them to reproduce the traced path.
* Whether `ATI Technologies Inc.` turns on AMD driver workarounds that hurt here. Compare with
  `METALGLDRV_VENDOR=metalgldrv` (VRAM then reads as unknown).
* Performance:
  * compressed sub-image uploads (about 13 k per run)
  * `glBindSampler` and `glBindTexture` churn (about 400 k each)
  * first-use pipeline compiles (MTL4Compiler at the first draw of each program variant)
  * per-frame `glClipControl` switches
* Multi-context sharing under the CGL frontend (four shared contexts; programs linked in one and used
  in another).
* The first launch builds a multi-GB virtual-texture cache and looks black for a long time
  (reported on other drivers too).
* Online services crash under Wine (Wine bug 42127). Use offline mode.
